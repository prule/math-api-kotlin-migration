# Design

## Context

See proposal.md (Why). The Java tests that hold observable assertions are `CalculationControllerTest` (MockMvc),
`ServiceHealthSmokeTest` (real HTTP) and `ApiDocumentationTest` (MockMvc). `CalculationTest`, `OperationTest`
and the ArchUnit tests are unit level, so they port in items 1 and 3, not here. Responses observed with curl
against the running Java service on 2026-11-10 are the evidence for RB-22 to RB-26.

## Goals / Non-Goals

**Goals:**
- One suite that runs unchanged against either service, using only `BASE_URL`.
- Every RB row is pinned by at least one contract test or golden case, tagged `// RB-n` so it can be found.
- Behaviour nobody thought to assert is caught by the golden diff.

**Non-Goals:**
- Running the suite in CI. That waits for item 6, when it can pass against Kotlin.
- RB-13 (the 500 handler). No HTTP input reaches it; the Java test calls the handler directly
  (`CalculationControllerTest.reportsAnUnexpectedFailureWithoutInternals`). Item 3 covers it with a unit test.
- Golden cases for `/v3/api-docs` and the Swagger UI HTML. Both are generated by springdoc, so their exact text
  will differ. The documentation tests pin their meaning.

## Decisions

1. **A Gradle JVM test suite** (`testing.suites.register<JvmTestSuite>("contractTest")`), not a hand-made
   source set and task. It's built in, it gets its own dependencies, and it is not wired into `check`. So
   `./gradlew build` stays service-free.
2. **The JDK `HttpClient`, forced to HTTP/1.1**, and Jackson `JsonNode` for reading JSON (as a contractTest
   dependency only). By default the JDK client tries an `h2c` upgrade, which adds headers neither service is
   asked about in production. Alternative: Ktor's client. Rejected, because the suite would then share a stack
   with the service it judges.
3. **`BASE_URL` is required.** Without it, the suite fails at once with a message. Pointing at the wrong service
   by default would make "green" meaningless.
4. **Assert what Java tests assert, plus what is observed. Spring's framework `detail` wording is not asserted.**
   For 404/405/406/415 the tests check status, `type=about:blank`, the reason-phrase title, `instance`, and the
   `Allow`/`Accept` headers. The `detail` text ("No static resource …") is recorded only in the golden files.
   Whether Kotlin must copy Spring's wording is decided in item 6, as an accepted difference.
5. **Golden responses: one JSON file, recorded and compared by the same code.** `GoldenResponsesContractTest`
   is a `@TestFactory`, with one dynamic test per corpus case. With `-Precord` it writes
   `src/contractTest/resources/golden/responses.json` instead of asserting. Each case stores the status, the
   `Content-Type`, `Allow`, `Accept` and `Location` headers, and the body: parsed JSON for JSON types (so key
   order doesn't matter), raw text otherwise. The base URL inside bodies (actuator `_links`) is replaced with
   `{base}`. Alternative: a separate shell script with per-case files. Rejected: it's two tools, and diffs are
   harder to read.
   **Record mode refuses to record any service but Java.** It checks first that `GET /error` returns Spring
   Boot's own error body (`"status":999`). Otherwise one run against Kotlin would quietly make the golden diff
   compare Kotlin with itself. The plan review asked for the guard. The first version keyed on the health
   content type, but RB-24 requires Kotlin to copy that type, so code review moved the guard to `/error`, which
   no RB row asks Kotlin to copy. `/error` must stay out of the corpus and out of the RB rows.
   The base URL is replaced with `{base}` in recorded headers as well as bodies.
6. **Corpus.** Every request body from the ported tests, plus generated cases:
   - each operation × operand pairs covering zeros in every form, signs, exponents (number and string), each
     limit and one past it (precision 100/101, scale ±1000/±1001), the DECIMAL128 rounding boundary, and
     trimmed and `+` strings;
   - protocol cases: each media type and method, a missing body, a trailing slash, YAML in and out;
   - each actuator path.
   That's about 130 cases, defined in Kotlin next to the test, so the corpus is reviewed like code. The
   operations come from the service's unknown-operation detail, and the invalid bodies are shared with
   `CalculationContractTest`, so no test lists the operations (STANDARDS.md §5). Case names must be unique, which is
   checked when the corpus is built.
7. **Retire `docs/JAVA-AUDIT.md`.** Its defects move to `docs/MIGRATION-LOG.md` → Source defects. Its "hidden
   behaviour" is already RB-8b. Keeping both would mean two places to update.

8. **The calculation tests don't depend on the API docs.** They check the unknown-operation detail's exact
   shape with a regex. Only `ApiDocumentationContractTest` compares the list with `/v3/api-docs`. Otherwise
   item 3 couldn't pass its own contract tests before item 5 adds the docs. (Found in code review.)
9. **Jackson 2 (`com.fasterxml`) throughout.** The suite uses jackson-databind 2.22.2, the version
   `ktor-serialization-jackson` 3.6.1 brings in, so item 3 adds no second Jackson. Jackson 3 (`tools.jackson`),
   which the Java service uses, is not used.

## Risks / Trade-offs

- [Golden bodies store a recorded `Content-Length`/chunking difference] → Only the named headers are stored.
  Transfer encoding is ignored.
- [The DECIMAL128 and huge-exponent cases are slow or flaky over HTTP] → The `< 1 s` check (RB-10) keeps the
  Java test's one-second budget. It runs locally only, never in CI.
- [The suite pins behaviour that is probably accidental (YAML support, health groups)] → That is intended: the
  suite characterises what exists. Dropping something later goes through Accepted differences with the user's
  agreement (CLAUDE.md, Apply step).
